# Архитектурное решение по логированию

## Мотивация

Когда клиент звонит с жалобой на пропавший заказ, разработчикам нужно лезть на сервер и вручную читать системные логи - если они вообще есть и если их никто не ротировал. Воспроизвести ситуацию со слов клиента практически невозможно.

Централизованное логирование меняет эту ситуацию: вся история событий сохраняется в одном месте, доступна для поиска по заказу, пользователю, временному промежутку.

### Что это даст компании

1. **Сокращение времени разбора инцидентов (MTTR)** - по `order_id` или `user_id` за секунды находим все события.
2. **Разгрузка поддержки** - менеджеры смогут самостоятельно смотреть историю заказа без привлечения разработчиков.
3. **Доказательная база при спорах с B2B-партнёрами** - можно предъявить лог с таймстампами.
4. **Выявление системных ошибок** - если один и тот же тип ошибки встречается 50 раз в день, это не баг-репорт, а системная проблема.
5. **Обнаружение аномалий** - внезапный рост количества ошибок или создание тысяч заказов за секунду могут быть симптомами атаки или бага в интеграции.

### Технические и бизнес-метрики, на которые повлияет внедрение логирования

1. **MTTR** - ожидаемое снижение с нескольких часов до десятков минут
2. **Количество эскалаций в разработку от поддержки** - снизится, поддержка сможет самостоятельно отвечать на вопросы по заказам
3. **Процент успешно доставленных заказов** - через логи выявим системные причины потерь и устраним их
4. **Стоимость производственного инцидента** - чем быстрее обнаружение и устранение, тем меньше клиентов успевает пострадать
5. **Время онбординга новых разработчиков** - с логами проще понять, как система работает, не нужно «общаться с живыми людьми, которые помнят»

## Какие логи собирать и из каких систем

### Системы, требующие логирования (все три бэкенда)

**Shop API** - начало пути каждого заказа  
**CRM API** - бизнес-решения: подтверждение заказа, закрытие  
**MES API** - расчёт стоимости, работа операторов, изменение статусов  

Фронтенды (Vue, React) - не включаем в серверное логирование. Ошибки на фронте логируются отдельными инструментами (Sentry, frontend error tracking) при необходимости.

**RabbitMQ** - логи брокера собираем отдельно (Filebeat -> Elasticsearch). Особенно важны события: недоставленное сообщение, DLQ, отключение потребителя.

### Список логов уровня INFO

**Shop API:**
- Создан новый заказ: `{timestamp, order_id, user_id, source: "online_shop"}`
- Загружен файл 3D-модели: `{timestamp, order_id, user_id, file_size_bytes, s3_key}`
- Заказ отправлен пользователем: `{timestamp, order_id, user_id, status: "SUBMITTED"}`
- Сообщение опубликовано в очередь: `{timestamp, order_id, queue_name, message_id}`
- Ответ отправлен клиенту: `{timestamp, order_id, http_status, duration_ms}`

**MES API:**
- Сообщение получено из очереди: `{timestamp, order_id, queue_name, message_id}`
- Начат расчёт стоимости: `{timestamp, order_id}`
- Завершён расчёт стоимости: `{timestamp, order_id, duration_ms, status: "PRICE_CALCULATED"}`
- Оператор взял заказ в работу: `{timestamp, order_id, operator_id, status: "MANUFACTURING_STARTED"}`
- Статус заказа изменён: `{timestamp, order_id, operator_id, old_status, new_status}`
- Сообщение опубликовано в очередь: `{timestamp, order_id, queue_name, message_id}`

**CRM API:**
- Сообщение получено из очереди: `{timestamp, order_id, queue_name, message_id}`
- Заказ подтверждён менеджером: `{timestamp, order_id, seller_id, status: "MANUFACTURING_APPROVED"}`
- Заказ закрыт: `{timestamp, order_id, seller_id, status: "CLOSED", reason}`
- Запрос к Shop DB: `{timestamp, query_type, duration_ms}` (без SQL-тела - безопасность)

### Логи уровня WARN и ERROR

**WARN** - нестандартная, но ожидаемая ситуация, не требующая немедленной реакции:
- Повторная попытка обработки сообщения из очереди (retry №1, №2)
- Расчёт стоимости занял более 20 минут (ещё в пределах нормы, но нужно знать)
- Пользователь пытается совершить действие, недоступное по бизнес-правилам (например, дважды отправить заказ)

**ERROR** - сбой, требующий реакции:
- Не удалось опубликовать сообщение в RabbitMQ (с деталями ошибки)
- Сообщение попало в DLQ (с `message_id`, `order_id`, описанием причины)
- Ошибка записи в БД: `{timestamp, order_id, error_type, error_message}`
- HTTP 5xx ответ отправлен клиенту: `{timestamp, endpoint, status_code, duration_ms, error_summary}`
- Расчёт стоимости завершился ошибкой: `{timestamp, order_id, error_message}`
- Не удалось достать файл из S3: `{timestamp, order_id, s3_key, error_message}`

**DEBUG** - детальная информация, используется только при расследовании проблем в dev/release окружениях. В prod отключён по умолчанию.

## Приоритет внедрения логирования и трейсинга

Команда не может одновременно внедрить логирование и трейсинг во всех системах. Предлагаю следующий порядок:

**Первый приоритет: MES API и Shop API**

Главная бизнес-проблема - потеря заказов. Почти весь критичный путь проходит через эти два сервиса и очередь. Если заказ пропал, он либо не вышел из Shop API, либо потерялся в MES. Логирование и трейсинг именно здесь дадут максимальный эффект немедленно.

Кроме того, Shop API и MES API - самые нагруженные сервисы после открытия B2B API. Видимость их работы критически важна.

**Второй приоритет: RabbitMQ**

Очередь - место, где заказы могут теряться молча. Сбор логов брокера (DLQ события, недоставленные сообщения) нужен параллельно с первым приоритетом, но технически это проще (Filebeat + уже существующий Elasticsearch).

**Третий приоритет: CRM API**

CRM API тоже важен (подтверждение заказов), но он менее нагружен и менее часто является точкой отказа по сравнению с MES и Shop. Его логирование внедряем третьим.

## Предлагаемое решение

### Технологический стек

Я выбираю **ELK-стек** (Elasticsearch, Logstash/Filebeat, Kibana).

**Почему ELK:**
- Широко известен, много документации, команда легко найдёт примеры
- Filebeat легко устанавливается на любой инстанс и собирает логи без изменения кода приложений
- Kibana предоставляет удобный UI для поиска логов по произвольным полям (order_id, user_id, timestamp)
- Elasticsearch легко масштабируется по мере роста данных
- Open source (базовый функционал бесплатен)

### Архитектура решения

1. **Структурированные логи** (JSON) - каждый бэкенд пишет логи в JSON-формате в stdout и в файл. Это стандарт для современных приложений, Spring Boot поддерживает через Logback + `logstash-logback-encoder`. C# - через Serilog с JSON-formatter.

2. **Filebeat** - устанавливается на каждый EC2-инстанс, собирает логи из файлов/stdout и отправляет в Logstash. Минимальная нагрузка на приложение, лёгкая конфигурация.

3. **Logstash** - принимает логи от Filebeat, обогащает (добавляет теги, парсит поля при необходимости), отправляет в Elasticsearch.

4. **Elasticsearch** - хранение логов. Отдельный кластер или тот же, что для трейсов (в нашем случае - один инстанс ES, разные индексы).

5. **Kibana** - визуализация, поиск, дашборды для поддержки и разработчиков.

### Политика безопасности

**Чувствительные данные:**
- В логах запрещено хранить: ФИО, email, адрес доставки, номер телефона, платёжные данные, содержимое 3D-файла.
- `user_id` и `order_id` - ПД-нейтральные идентификаторы, их логировать можно.
- При передаче заказа на доставку - адрес в лог не пишем, только `order_id`.
- Правило обязательно зафиксировать в инженерном гайде и проверять на code review.

**Доступ к Kibana:**
- Только через внутреннюю сеть / VPN.
- Разработчики и DevOps - полный доступ на чтение.
- Поддержка (менеджеры по продажам, продакт) - доступ к бизнес-дашбордам (поиск по order_id без просмотра технических деталей). Отдельная роль в Kibana.
- Операторы MES и продавцы CRM - нет прямого доступа к логам. Если нужно посмотреть историю заказа - через поддержку.

### Политика хранения

- Логи уровня INFO и выше хранятся **30 дней** в горячем хранилище Elasticsearch.
- После 30 дней - перемещаются в холодное хранилище на **6 месяцев** (для разбора давних инцидентов и споров с B2B-партнёрами).
- Логи уровня ERROR - **6 месяцев** в горячем хранилище. Ошибки важны для постмортем-анализа.
- Отдельный индекс на каждое окружение (dev, release, prod): `logs-prod-*`, `logs-release-*`.
- Index Lifecycle Management (ILM) в Elasticsearch настраивает ротацию автоматически.

Примерная оценка объёма: 100 заказов/день * рост * несколько событий на заказ = несколько тысяч событий/день. Даже с учётом системных логов - это небольшой объём для Elasticsearch. На ближайший год один умеренный EC2 с хорошим диском справится.

## Алертинг и анализ аномалий

### Алертинг на основе логов

В Kibana (или Grafana с Elasticsearch datasource) настраиваем следующие алерты:

- **DLQ событие** - любое сообщение об ошибке с маркером `dlq` -> немедленный алерт в Slack.
- **Рост HTTP 500** - более 10 ERROR-записей в минуту -> алерт разработчику.
- **Ошибка расчёта стоимости** - `error_type: price_calculation_failed` -> алерт дежурному разработчику.
- **Долгий расчёт стоимости** - лог `{status: price_calculating, duration_ms > 1800000}` -> WARN-алерт (возможно зависание).

### Обнаружение аномалий

**Пример с DDoS / аномальным ростом:**
Если за последние 60 секунд количество событий `{event: order_created}` выросло более чем в 10 раз по сравнению со скользящим средним за предыдущий час - это аномалия. Может быть:
- DDoS с использованием функции создания заказов
- Баг в интеграции B2B-партнёра (бесконечный цикл)
- Реальный вирусный рост трафика (маловероятно, но приятно)

В Kibana это можно настроить через Machine Learning (SIEM) или через простое правило в Watcher: "если count(order_created за последнюю минуту) > 5 * avg(order_created за предыдущий час)". При срабатывании - алерт + автоматический тикет в трекер.

## Дополнительное задание: выбор технологии для работы с логами

| Критерий | ELK (Elastic) | OpenSearch | Splunk | Loki + Grafana |
|---|---|---|---|---|
| **Лицензия** | Elastic License v2 (не полностью OSS с 2021) | Apache 2.0 (форк Elastic) | Проприетарная | Apache 2.0 |
| **Стоимость** | Бесплатно в базовой конфигурации, Enterprise - платно | Бесплатно | Дорого ($150+/GB в managed) | Бесплатно |
| **Простота развёртывания** | Умеренная (Filebeat + Logstash + ES + Kibana) | Аналогично ELK | Агент + Splunk Server, проще для команды без опыта ELK | Прост в деплое, но менее богатый UI |
| **Поиск по произвольным полям** | Полнотекстовый поиск + KQL | Аналогично ELK | Хорошо, SPL-язык | Поиск по labels, хуже по содержимому |
| **Экосистема и интеграции** | Широкая, много плагинов, Spring Boot / Serilog из коробки | Аналогично ELK, плюс AWS OpenSearch Managed | Широкая, сильная enterprise-интеграция | Тесная интеграция с Prometheus/Grafana |
| **Знание в команде** | Наиболее популярен, легко нанять | Менее известен, но похож на ELK | Требует специалистов | Может быть новым для команды |
| **Масштабируемость** | Горизонтально масштабируется хорошо | Аналогично ELK | Хорошо, но дорого | Хорошо для больших объёмов |

**Вывод:** выбираю **ELK**. Несмотря на изменение лицензии Elastic в 2021 году, базовый функционал (который нам нужен) остаётся бесплатным. ELK широко известен, у нас один DevOps и небольшая команда - наём или консультация по ELK проще, чем по OpenSearch. Splunk слишком дорог для нашего масштаба. Loki + Grafana интересен как альтернатива (особенно если мы уже разворачиваем Grafana для мониторинга), но его поиск по содержимому слабее, что критично для разбора инцидентов.
