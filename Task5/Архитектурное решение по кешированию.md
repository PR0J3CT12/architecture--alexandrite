# Архитектурное решение по кешированию

## Мотивация

Есть две связанные, но разные проблемы:

1. **Медленный дашборд MES** - операторы жалуются, что первая страница со списком заказов грузится долго. Добавление пагинации и фильтров не помогло. Это значит, что проблема не в объёме данных, передаваемых на фронтенд, а в скорости запроса к базе данных. Запрос тяжёлый - вероятно, нет нужных индексов, либо запрос читает большой объём строк, даже с фильтрами.

2. **Медленное выполнение заказов с точки зрения клиента** - клиенты недовольны скоростью. Здесь проблема скорее всего в другом: заказы зависают из-за ненадёжности очереди, а не из-за производительности MES per se. Но если MES API медленно отвечает, это тоже влияет на операторов.

Кеширование решает первую проблему - дашборд операторов. Именно на нём я и сосредоточусь.

**Что предлагаю закешировать:**
- Список заказов на дашборде MES (первая страница, отображение по статусам с пагинацией)

**Что не имеет смысла кешировать:**
- Статусы отдельных заказов - они меняются часто, кеш будет постоянно инвалидироваться
- 3D-файлы - уже хранятся в S3, это и есть их постоянное хранилище
- Данные аутентификации - не наша зона

---

## Предлагаемое решение

### Клиентское или серверное кеширование?

Выбираю **серверное кеширование**.

Клиентское кеширование (HTTP-заголовки `Cache-Control`, `ETag`) подходит для статических или редко меняющихся ресурсов, которые одинаковы для всех пользователей: картинки, JS-бандлы, справочники. Список заказов - динамические данные, которые меняются при каждом изменении статуса. Оператор А и оператор Б видят одинаковый дашборд, но он обновляется постоянно. Если кешировать на клиенте с достаточно коротким TTL, мы просто перекладываем нагрузку на клиента без реального облегчения для базы данных. При длинном TTL операторы будут видеть устаревшие данные, что напрямую влияет на их вознаграждение - они могут пропустить новый заказ.

Серверный кеш (Redis) позволяет:
- Все операторы разделяют один кеш, который обновляется по событию, а не по таймеру
- База данных разгружена - один запрос наполняет кеш, который потом отдаёт данные многим операторам
- Легко управлять инвалидацией на стороне сервера

### Паттерн кеширования: Cache-Aside

Выбираю **Cache-Aside** (Lazy Loading).

**Как работает:**
1. Запрос дашборда приходит в MES API
2. MES API сначала смотрит в Redis: есть ли кешированный список заказов?
3. Если **cache hit** - отдаём из Redis, без обращения к БД
4. Если **cache miss** - идём в MES DB, читаем список, сохраняем в Redis, отдаём клиенту

**Почему Cache-Aside, а не другие паттерны:**

*Write-Through* - при каждой записи данных в БД сразу обновляется кеш. Проблема: изменения в MES происходят часто (статусы заказов меняются постоянно), а дашборд читает агрегированный список. Каждая смена статуса - это потенциальное обновление кеша. Это создаёт лишние операции записи и усложняет логику: нужно чётко понимать, какие именно изменения влияют на кешированный список. В нашем случае это сложнее, чем кажется - список отображает заказы по статусам с фильтрами.

*Refresh-Ahead* - кеш обновляется превентивно, до того как он истечёт. Хорош, когда чётко известно, что данные будут нужны снова. Но это добавляет фоновую нагрузку на БД и сложность инфраструктуры. Для дашборда с переменной активностью операторов это избыточно.

*Cache-Aside* - самый простой и предсказуемый. Нет риска «потерять» обновление данных, потому что при cache miss всегда идём в источник истины. Легко сочетается с event-driven инвалидацией.

### Диаграмма последовательности

#### Чтение списка заказов (операция read)

```
Operator           MES Frontend         MES API                Redis              MES DB
    │                    │                 │                     │                  │
    │── open dashboard ─►│                 │                     │                  │
    │                    │── GET /orders ─►│                     │                  │
    │                    │                 │── GET orders:list ─►│                  │
    │                    │           [cache hit]                 │                  │
    │                    │                 │◄── orders JSON ─────│                  │
    │                    │◄── 200 orders ──│                     │                  │
    │◄── render table ───│                 │                     │                  │
    │                    │          [cache miss]                 │                  │
    │                    │                 │──── SELECT orders ────────────────────►│
    │                    │                 │◄──────────── orders rows ──────────────│
    │                    │                 │── SET orders:list TTL=60s ────────────►│
    │                    │                 │                     │                  │
    │                    │◄── 200 orders ──│                     │                  │
    │◄── render table ───│                 │                     │                  │
```

#### Изменение статуса заказа (операция write + инвалидация кеша)

```
Operator          MES Frontend                            MES API                 Redis          MES DB             RabbitMQ
    │                    │                                    │                     │               │                  │
    │── take order ─────►│                                    │                     │               │                  │
    │                    │─ POST /orders/{id}/start ─────────►│                     │               │                  │
    │                    │                                    │── UPDATE status ───────────────────►│                  │
    │                    │                                    │◄──────────── ok ────────────────────│                  │
    │                    │                                    │── DEL orders:list ─►│               │                  │
    │                    │                                    │◄── ok ──────────────│               │                  │
    │                    │◄─────── 200 ok ────────────────────│                     │               │                  │
    │◄── order updated ──│                                    │                     │               │                  │
    │                    │                                    │── publish to RabbitMQ (order_status_changed event)────►│
```

После инвалидации кеша следующий запрос на дашборд выполнит cache miss и обновит Redis из БД.

### Стратегия инвалидации кеша

Я выбираю **комбинированную стратегию: event-driven инвалидация + TTL как страховка**.

#### Основная стратегия: инвалидация по событию (programmatic / event-driven)

При каждом изменении статуса заказа в MES API - явно удаляем кеш-ключ `orders:list` из Redis.

**Почему это основная стратегия:**
- Операторам критически важно видеть актуальные данные - от этого зависит их вознаграждение (кто первый взял заказ)
- Устаревший кеш даже на 30 секунд может привести к тому, что два оператора одновременно возьмут один заказ, или оператор пропустит новый заказ

**Ключи кеша:**
- `orders:list:{status_filter}:{page}` - отдельный ключ для каждой комбинации фильтра и страницы. При изменении статуса инвалидируем все ключи по паттерну `orders:list:*` (или используем тег-инвалидацию через Redis Tags).

#### Страховочная стратегия: TTL 60–120 секунд

Даже с event-driven инвалидацией устанавливаем TTL на кеш-записи. Это защита на случай:
- Баг в коде, который не прислал событие инвалидации
- Прямое изменение БД в обход API (например, при мигации данных)
- Сбой в Redis при записи инвалидации

TTL 60–120 секунд - разумный баланс: оператор увидит обновлённые данные максимум через 2 минуты, даже если event-driven инвалидация не сработала.

#### Почему не только TTL

Только временная стратегия создаёт постоянную задержку видимости. Оператор открывает дашборд и видит список, который может быть устаревшим до 2 минут. При конкуренции за заказы это неприемлемо. Кроме того, при высокой нагрузке TTL нужно делать очень коротким, что сводит на нет смысл кеша (частые cache miss).

#### Почему не только event-driven инвалидация

Только event-driven без TTL создаёт риск вечного кеша при пропуске события инвалидации. TTL - это надёжная страховка с минимальными накладными расходами.

### Сравнение стратегий инвалидации

| | Event-driven (programmatic) | TTL | Write-Through | Refresh-Ahead |
|---|---|---|---|---|
| **Актуальность данных** | Мгновенная после события | С задержкой до TTL | Мгновенная | Может быть устаревшей |
| **Сложность реализации** | Умеренная (нужно везде инвалидировать) | Минимальная | Высокая (сложно при агрегированных данных) | Высокая |
| **Риск устаревшего кеша** | Низкий (если события не теряются) | Есть (в пределах TTL) | Очень низкий | Низкий |
| **Нагрузка на БД** | Низкая | Зависит от TTL | Каждая запись = обновление кеша | Фоновая нагрузка |
| **Подходит для нашего случая** | **Да - основная** | **Да - страховка** | Нет - сложно с агрегатом | Нет - избыточно |

**Итог:** используем комбинацию event-driven инвалидации (основная) + TTL 60–120 секунд (страховочная). Это даёт максимальную актуальность данных при минимальной нагрузке на БД.

## Технологический стек

**Redis** - выбор очевиден для серверного кеша в нашем контексте:
- Нативная поддержка TTL на уровне ключа
- Операция DEL (инвалидация) - O(1)
- Клиенты для Java (Lettuce, Redisson) и C# (StackExchange.Redis) отлично развиты
- Managed Redis доступен в Yandex Cloud
- Минимальный latency (< 1 мс для большинства операций)

Развёртывание: Managed Redis в Yandex Cloud с одним primary инстансом (на первом этапе replica не нужна - если Redis недоступен, MES API просто идёт в БД).
