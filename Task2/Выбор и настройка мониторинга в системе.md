# Выбор и настройка мониторинга в системе

## Мотивация

Сейчас «Александрит» узнаёт о проблемах со слов клиентов - через менеджеров по продажам или напрямую через поддержку. Это означает, что к моменту, когда команда начинает разбираться в проблеме, клиент уже пострадал: заказ завис, дедлайн сорван, доверие потеряно.

Добавление мониторинга позволит команде узнавать о деградации раньше, чем это заметят пользователи.

Конкретные эффекты для компании:

- **Сокращение времени реакции на инциденты (MTTR)**. Сейчас разбор занимает часы или дни, потому что нет никаких данных. С мониторингом - минуты, потому что сразу видно, что именно сломалось и когда.
- **Видимость очереди заказов**. Главная боль - потеря заказов через RabbitMQ. Мониторинг очереди позволит увидеть накопление сообщений и попадание в DLQ в реальном времени.
- **Обоснование для масштабирования**. Без данных невозможно аргументировать найм DevOps или добавление инстансов. С метриками CPU, памяти и latency - легко показать бизнесу, когда инфраструктура перестаёт справляться.
- **Контроль SLA с B2B-партнёрами**. После открытия внешнего API появились обязательства перед клиентами-компаниями. Без мониторинга невозможно ни контролировать их соблюдение, ни доказать, что проблема была на стороне партнёра, а не «Александрита».
- **Планирование ёмкости**. Нагрузка растёт на 100 заказов в месяц. Метрики помогут предсказать, когда текущих ресурсов станет недостаточно, и подготовиться заранее.

## Выбор подхода к мониторингу

Для разных частей системы я использую разные подходы:

**API-сервисы (Shop API, CRM API, MES API) - RED**

RED (Rate, Errors, Duration) - это метод, специально заточенный под сервисы, обрабатывающие запросы. Для наших API это самый естественный фрейм: нас интересует, сколько запросов в секунду обрабатывается, сколько из них завершается с ошибкой и как долго они выполняются.

**Инфраструктура (EC2, БД) - USE**

USE (Utilization, Saturation, Errors) хорошо подходит для ресурсов: CPU, память, диск, сеть. Позволяет ответить на вопрос «ресурс исчерпан?» раньше, чем это проявится в поведении API.

**RabbitMQ и очередь заказов - «Четыре золотых сигнала»**

Для очереди сообщений важнее всего понимать: растёт ли очередь (насыщенность), есть ли ошибки (сообщения в DLQ). Latency и traffic здесь вторичны.

## Выбранные метрики

### RabbitMQ

**Number of dead-letter-exchange letters**
Это самая важная метрика для нас прямо сейчас. Каждое сообщение в DLQ - это потенциально потерянный заказ. Без неё мы не знаем, сколько сообщений «упало» и не обработалось.
Ярлыки: `queue_name` (чтобы различать, в какой именно очереди накапливаются ошибки: заказы, статусы, уведомления).

**Number of messages**
Количество сообщений, которые были получены потребителем, но ещё не подтверждены. Рост этой метрики говорит о том, что потребитель завис или перегружен.
Ярлыки: `queue_name`.

### Shop API

**Number of requests (RPS) for internet shop API**
Нужна, чтобы понимать нормальный уровень нагрузки и замечать аномальные всплески (например, DDoS или резкий рост пользователей).
Ярлыки: `method`, `endpoint`.

**Response time (latency) for shop API**
Время ответа API - прямой индикатор пользовательского опыта.
Ярлыки: `endpoint`, `method`, `status_code`.

**Number of HTTP 200 for shop API**
Количество успешных ответов. В связке с HTTP 500 позволяет считать error rate.
Ярлыки: `endpoint`.

**Number of HTTP 500 for shop API**
Серверные ошибки - прямой сигнал о проблемах. Рост этой метрики должен немедленно уходить в алерт.
Ярлыки: `endpoint`, `method`.

**CPU % for shop API**
Нагрузка на процессор инстанса. Нужна для понимания, не перегружен ли сервер. При стабильном росте - сигнал к добавлению инстансов или оптимизации.
Ярлыки: нет (один инстанс на сервис, пока).

**Memory Utilisation for shop API**
Потребление памяти. Утечка памяти - распространённая проблема в Java-приложениях; эта метрика позволяет её заметить заблаговременно.
Ярлыки: нет.

**Number of connections for shop db instance**
Количество активных соединений с БД. Исчерпание пула соединений приводит к ошибкам при запросах - эту ситуацию нужно предупреждать.
Ярлыки: нет.

**Size of shop db instance**
Размер базы данных. Нужна для планирования ёмкости: когда заканчивается место, БД перестаёт принимать записи. Managed service в Yandex Cloud имеет лимиты.
Ярлыки: нет.

**Size of S3 storage**
Хранилище 3D-файлов может расти быстро, особенно с ростом числа заказов. Нужно знать заранее, когда нужно увеличивать лимит или чистить старые файлы.
Ярлыки: нет.

**Number of simultaneous sessions for shop API**
Количество одновременных пользователей. В сочетании с CPU и latency помогает понять, при каком уровне активности сервис начинает деградировать.
Ярлыки: нет.

### CRM API

**Number of requests (RPS) for CRM API**
Аналог для CRM. Продавцов значительно меньше, чем покупателей, поэтому трафик здесь ниже - но важно видеть аномалии.
Ярлыки: `method`, `endpoint`.

**Response time (latency) for CRM API**
Продавцы работают с CRM профессионально, медленный интерфейс напрямую влияет на их продуктивность.
Ярлыки: `endpoint`, `method`, `status_code`.

**Number of HTTP 500 for CRM API**
Серверные ошибки, как и для Shop API, требуют немедленного внимания.
Ярлыки: `endpoint`.

**CPU % for CRM API / Memory Utilisation for CRM API**
Ресурсные метрики инстанса. Нужны для планирования ёмкости.
Ярлыки: нет.

### MES API

**Number of requests (RPS) for MES API**
Важно отслеживать в том числе RPS от внешних API-пользователей (B2B). Нужно разделять трафик от операторов и от API-партнёров.
Ярлыки: `method`, `endpoint`, `client_type` (internal/external).

**Number of requests (RPS) per user for MES API**
Особенно актуально для внешнего API. Позволяет видеть, кто из партнёров генерирует аномально высокую нагрузку, и подготовить почву для rate limiting.
Ярлыки: `user_id` / `api_client_id`.

**Response time (latency) for MES API**
Медленный дашборд операторов - уже известная проблема. Эта метрика позволит видеть, улучшилась ли ситуация после оптимизаций.
Ярлыки: `endpoint`, `method`.

**Number of HTTP 500 for MES API**
Серверные ошибки, алерт при росте.
Ярлыки: `endpoint`.

**CPU % for MES API / Memory Utilisation for MES API**
Ресурсы инстанса MES API. C#-сервис с расчётом стоимости 3D-моделей может давать пики по CPU во время сложных вычислений.
Ярлыки: нет.

**Memory Utilisation for MES db instance / Number of connections for MES db instance**
MES DB хранит все производственные данные и является источником медленных запросов. Важно видеть загрузку.
Ярлыки: нет.

**Size of MES db instance**
Рост объёма данных о заказах и операциях со временем.
Ярлыки: нет.

### Метрики, которые я не выбрал

- **Kb transferred (received/sent)** - это полезно для мониторинга сети, но сейчас не является приоритетом, учитывая проблемы с заказами и производительностью. Можно добавить позже.
- **Number of RPS per user for shop/CRM API** - для B2C это нецелесообразно: пользователей много, а вклад одного незначителен. Для CRM продавцов мало, и специфика их работы не предполагает аномальных всплесков.

## Дополнительное задание: показатели насыщенности

### RabbitMQ: количество сообщений в очереди
**Пороговое значение**: > 1000 сообщений в основных очередях (заказы, статусы).
**Почему**: при нормальной работе очереди обрабатываются почти мгновенно. Накопление говорит о том, что потребитель не справляется или упал.
**Действие при превышении**: алерт дежурному. Параллельно проверяем статус потребителей (MES API, CRM API).

### CPU % для API-сервисов
**Пороговое значение**: > 80% в течение 5 минут.
**Почему**: выше 80% CPU начинаются задержки в обработке запросов, GC в JVM работает хуже, возможны таймауты.
**Действие**: алерт дежурному DevOps. Краткосрочно - перезапуск/рестарт инстанса, среднесрочно - добавление второго инстанса и настройка auto-scaling.

### Memory Utilisation для API-сервисов
**Пороговое значение**: > 85%.
**Почему**: при достижении предела приложение начинает активно использовать GC (Java) или swap, что сильно замедляет работу. При 95% возможен OOM kill.
**Действие**: алерт дежурному. Проверяем, нет ли утечки памяти в последнем деплое. Если нет - увеличиваем тип инстанса.

### Number of connections для БД
**Пороговое значение**: > 80% от max_connections (обычно это ~80–90 соединений из 100).
**Почему**: исчерпание пула соединений вызывает ошибки на стороне приложения немедленно.
**Действие**: алерт DevOps, проверить PgBouncer (если не настроен - настроить connection pooler). Временно - увеличить max_connections или перезапустить приложение, которое держит лишние соединения.

### DLQ: количество сообщений в dead letter exchange
**Пороговое значение**: > 0 (любое сообщение в DLQ - это потенциально потерянный заказ).
**Почему**: DLQ - это индикатор серьёзных сбоев в обработке. Каждое сообщение там требует ручного или автоматического анализа.
**Действие**: немедленный алерт. Дежурный разработчик просматривает содержимое DLQ, понимает причину и исправляет.

1. **Развернуть Prometheus** - инстанс на Yandex Cloud (EC2 или managed). Настроить сбор метрик для инфраструктурных метрик (CPU, RAM, диск).

2. **Подключить метрики приложений**

3. **Подключить метрики RabbitMQ**

4. **Подключить метрики PostgreSQL**

5. **Развернуть Grafana** - подключить Prometheus как datasource, создать дашборды:
   - Общий обзор: RPS, error rate, latency по всем трём API.
   - RabbitMQ дашборд: очереди, DLQ, in-flight.
   - Инфраструктурный: CPU, RAM, диск, соединения к БД.

6. **Настроить алертинг** - в Grafana Alerting или через Alertmanager:
   - Алерт на DLQ > 0.
   - Алерт на HTTP 500 rate > 1% в течение 2 минут.
   - Алерт на p95 latency > 3 секунд.
   - Алерт на CPU > 80% в течение 5 минут.
   - Алерт на количество сообщений в основных очередях > 1000.
   - Доставка уведомлений: Slack для info/warning, звонок для critical.

7. **Подключить S3 метрики**
