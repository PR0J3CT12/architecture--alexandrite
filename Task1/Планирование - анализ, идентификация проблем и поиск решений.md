# Планирование: анализ, идентификация проблем и поиск решений

## Контекст

Компания «Александрит» - производитель ювелирных украшений с онлайн-магазином, позволяющим заказать изделие по кастомному 3D-дизайну. Система состоит из трёх приложений:

- **Онлайн-магазин** (Vue + Spring Boot)
- **CRM** (Vue + Spring Boot) - для продавцов
- **MES** (React + C#) - для операторов производства

Интеграция MES ↔ CRM реализована через RabbitMQ. MES считает стоимость изделия по 3D-модели от 2 до 30 минут. Недавно открыт внешний API для партнёров (B2B), через который MES принимает заказы, а CRM создаёт их на основе сообщений из очереди.

---

## Проблемные места

### 1. Потеря и зависание заказов в очереди сообщений

Судя по всему, главная причина пропавших заказов - ненадёжная работа RabbitMQ. Если сообщение теряется или не обрабатывается - заказ просто зависает в промежуточном состоянии, и никто об этом не знает.

Дополнительно: нет идемпотентности при обработке сообщений. Если потребитель упал после частичной обработки и сообщение попало повторно, может создаться дубль.

### 2. Отсутствие наблюдаемости (observability)

Нет мониторинга, нет централизованного логирования, нет трейсинга. Единственный источник информации о проблемах - слова клиентов. Команда не видит, где именно зависает заказ: в Shop API, в очереди, в MES или в CRM. Любая диагностика занимает много времени.

### 3. Медленная работа дашборда MES

Операторы жалуются, что первая страница MES грузится долго. Добавление пагинации и фильтров не помогло. Скорее всего, проблема в тяжёлом запросе к базе данных - либо отсутствуют нужные индексы, либо запрос сложный (несколько JOIN, сортировка, большой объём данных). При этом нагрузка продолжает расти.

### 4. Единственный инстанс каждого сервиса - нет горизонтального масштабирования

Каждое приложение работает на одном EC2-инстансе, базы данных - тоже по одному инстансу. При росте нагрузки система не масштабируется. Любой сбой инстанса приводит к полному недоступности сервиса.

### 5. Базы данных без реплик для чтения

Shop DB используется и Shop API, и CRM API - они конкурируют за ресурсы одного инстанса. MES DB тоже работает в режиме single-node. Нет read replica - при увеличении читающих запросов (например, дашборд MES) СУБД начинает тормозить.

### 6. Отсутствие алертинга и dead letter exchange в RabbitMQ

Нет видимости количества сообщений в очереди, нет DLX для недоставленных сообщений. Сообщение может просто пропасть - и никто не узнает.

### 7. QA-процесс - узкое место в релизном цикле

Ручное E2E-тестирование тормозит деплой. Если QA-инженер находит high/highest баг, релиз откладывается на неопределённый срок. Задержки растут. Автоматизация тестирования минимальная.

### 8. Нет rate limiting и защиты внешнего API

После открытия B2B API нет ограничений на количество запросов от партнёров. Один партнёр может перегрузить MES API и повлиять на работу всего сервиса.

### 9. Ручной деплой в prod и release

Деплой в production и release-окружения происходит вручную. Это снижает частоту деплоев, увеличивает вероятность ошибок и задерживает доставку исправлений.

### 10. Нет обработки долгих асинхронных операций на стороне пользователя

MES считает стоимость 2–30 минут. Пользователь онлайн-магазина не получает никакого промежуточного статуса, пока идёт расчёт. Если что-то пошло не так - он об этом не узнает.

## Список инициатив (в порядке приоритета)

### Приоритет 1 - Добавить базовую наблюдаемость, чтобы с помощью него оценить эффективность остальных инициатив

**Инициатива 2. Добавить централизованное логирование**
- Развернуть ELK-стек (Elasticsearch, Logstash/Filebeat, Kibana)
- Настроить структурированное логирование во всех трёх бэкендах
- Логировать все изменения статусов заказа с контекстом (orderId, timestamp, actor)

**Инициатива 3. Добавить мониторинг инфраструктуры и сервисов**
- Развернуть Prometheus + Grafana
- Собирать метрики с RabbitMQ, всех API, баз данных
- Настроить алертинг на критические события: очередь растёт, API возвращает 5xx, БД перегружена

### Приоритет 2 - Решить проблему производительности MES и устранить потерю заказов

**Инициатива 1. Настроить надёжность RabbitMQ**
- Включить durable queues и persistent messages
- Настроить dead letter exchange (DLX) для недоставленных/отклонённых сообщений
- Настроить явные ack/nack при обработке сообщений
- Добавить retry-логику с exponential backoff

**Инициатива 4. Оптимизировать запросы и добавить кеширование для MES-дашборда**
- Проанализировать slow query log, добавить индексы
- Добавить серверное кеширование (Redis) для списка заказов операторов
- Рассмотреть CQRS-подход: отдельные модели для чтения и записи

**Инициатива 5. Добавить read replica для MES DB и Shop DB**
- Все запросы на чтение (дашборд, аналитика) направлять в реплику
- Запись - только в primary

### Приоритет 3 - Масштабирование и отказоустойчивость

**Инициатива 6. Горизонтальное масштабирование сервисов**
- Добавить load balancer перед каждым API
- Запустить минимум два инстанса каждого сервиса
- Настроить auto-scaling по нагрузке (CPU, RPS)

**Инициатива 7. Добавить трейсинг**
- Развернуть Jaeger / Zipkin
- Пробросить trace ID через все сервисы и очередь
- Это позволит видеть полный путь заказа и находить точку зависания

**Инициатива 8. Добавить rate limiting для внешнего API**
- Ограничить количество запросов от одного API-клиента
- Вернуть HTTP 429 при превышении лимита
- Можно реализовать на уровне API Gateway или nginx

### Приоритет 4 - Улучшение процессов

**Инициатива 9. Автоматизировать E2E-тесты**
- Приоритизировать критичные сценарии: создание заказа, смена статуса, расчёт стоимости
- Написать авто-тесты, чтобы убрать зависимость от ручного тестирования перед каждым релизом

**Инициатива 10. Внедрить автоматический деплой в release-окружение**
- Добавить шаг в CI/CD pipeline: автодеплой в release после прохождения тестов
- Деплой в prod оставить ручным, но упростить его (кнопка в CI, не команды вручную)

## Ход рассуждений

### Целевая архитектура через полгода

Через полгода я вижу систему, в которой исчезнет основная проблема - потеря заказов - и появится инструментарий, позволяющий быстро находить и диагностировать новые проблемы.

Конкретно:

1. **RabbitMQ** настроен надёжно: DLX, durable queues, retry. Каждое потерянное сообщение попадает в dead letter queue и уходит в алерт к команде.

2. **Observability stack**: Prometheus + Grafana для метрик, ELK для логов, Jaeger для трейсинга. По trace ID можно пройти весь путь заказа - от создания в онлайн-магазине до отправки покупателю.

3. **MES дашборд** работает быстро: Redis-кеш для списка заказов, оптимизированные индексы, возможно, read replica.

4. **Горизонтальное масштабирование**: каждый API работает на 2+ инстансах за load balancer. Базы имеют read replica.

5. **Rate limiting** на внешнем B2B API: партнёры ограничены по количеству запросов.

6. **Автотесты** покрывают критичные сценарии, ручное E2E тестирование перестало быть блокером релизов.

Архитектура остаётся монолитной в части приложений - переход к микросервисам сейчас не приоритет и не нужен при текущих масштабах. Команда небольшая, и декомпозиция создаст больше накладных расходов, чем решит проблем.

### Три приоритетных пункта на ближайшие полгода

Если бы пришлось выбрать только три - я бы выбрал:

**1. Настройка надёжности RabbitMQ (Инициатива 1)**

Это корень проблемы. Клиенты теряют заказы - это напрямую бьёт по репутации и деньгам. Решается относительно быстро (конфигурация, небольшие доработки кода обработчиков) и даёт немедленный эффект. Без этого все остальные улучшения не помогут - заказы будут продолжать теряться.

**2. Централизованное логирование + мониторинг (Инициативы 2 и 3)**

До тех пор, пока нет наблюдаемости, мы работаем вслепую. Нельзя нормально диагностировать проблемы, нельзя оценить эффект от изменений. Это инвестиция, которая окупится буквально сразу - уже через неделю после внедрения команда начнёт видеть то, чего раньше не замечала. Инициативы 2 и 3 объединяю, потому что разворачивать их стоит вместе: один DevOps, одна инфраструктурная задача.

**3. Кеширование и оптимизация дашборда MES (Инициатива 4)**

Медленный дашборд - это ежедневная боль операторов, которая уже снижает их производительность. От вознаграждения операторов зависит их мотивация, а от мотивации - скорость производства. Это тоже бизнес-проблема. Кеш на список заказов с правильной инвалидацией - конкретная, ограниченная задача с ощутимым результатом.

Горизонтальное масштабирование (Инициатива 6) - важно, но сейчас нагрузка ещё не достигла точки, когда один инстанс не справляется по CPU/RAM. Проблема не в пропускной способности инстансов, а в потере заказов и медленных запросах. Масштабирование без устранения этих проблем только размажет боль на больше инстансов.
